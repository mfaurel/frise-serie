# Architecture Patterns — Frise Série Historical Timeline

**Domain:** Interactive parallax horizontal timeline (Next.js App Router)
**Researched:** 2026-05-17
**Overall confidence:** HIGH (primary claims verified via official docs and Motion.dev)

---

## 1. Parallax Scroll Engine

### Recommendation: Framer Motion (Motion) `useScroll` + `useTransform`

**Rationale:** Motion (the rebranded Framer Motion) is the only React animation library that runs scroll-linked animations on the browser's native `ScrollTimeline` API where available, giving hardware-accelerated compositor-thread animations without JavaScript overhead. The `useScroll` / `useTransform` pair maps scroll progress to per-layer translation values with a clean, declarative API.

CSS Scroll-Driven Animations (`animation-timeline: scroll()`) are faster in theory but are still impractical here because:
- They cannot be driven by a custom non-linear time scale (year → pixel mapping logic must run in JS)
- Safari support is incomplete as of 2026-05-17
- iOS 13+ broke the classic CSS 3D parallax technique with `perspective`

`requestAnimationFrame` raw loops are inferior to Motion because Motion already uses RAF internally and adds scroll-progress memoization, Spring physics, and layout-aware callbacks.

**Pattern — horizontal scroll driven by vertical page scroll:**

```typescript
// The timeline container is a tall div that pins the viewport
// Vertical scroll progress drives horizontal translation
const containerRef = useRef<HTMLDivElement>(null);
const { scrollYProgress } = useScroll({ target: containerRef });

// Background (era illustrations): slow layer — moves ~40% of total offset
const bgX = useTransform(scrollYProgress, [0, 1], ["0%", "-60%"]);

// Axis + events: medium layer — moves 1:1 with the fresco
const axisX = useTransform(scrollYProgress, [0, 1], ["0%", "-100%"]);

// Show cards: fast layer — 1:1 or slightly faster for depth
const cardsX = useTransform(scrollYProgress, [0, 1], ["0%", "-100%"]);
```

The outer container sets `height: "500vh"` (calibrate for full fresco width); the inner wrapper uses `position: sticky; top: 0; height: 100vh; overflow: hidden`.

**Alternative approach (horizontal native scroll):** If native horizontal swipe on mobile is preferred, use a `overflow-x: scroll` container and `useScroll({ axis: "x" })`. The parallax layers still use `useTransform` but from `scrollXProgress`. This is simpler on mobile but loses smooth-scroll control and requires `scroll-snap` for era alignment.

**Decision for this project:** Start with the vertical-scroll-drives-horizontal-x approach (sticky inner container). It gives the most cinematic feel, full keyboard support, and works consistently across iOS Safari. The non-linear year-to-pixel scale is implemented in the JavaScript layer before the pixel offset is fed into `useTransform` as an input range.

**Non-linear time scale:** Pre-compute a `yearToPixel(year: number): number` mapping function that uses logarithmic or segment-linear scaling. The entire fresco width is a fixed large number (e.g., 20 000 px for the content layer). Card positions and era widths are computed from this function at data-load time.

## 2. Data Architecture

### Recommendation: Static JSON at build time, promote to DB only for user features (post-launch)

**For v1 (no user accounts):**

```
/data
  shows.json         // array of ~100-150 Show objects (full model)
  eras.json          // array of HistoricalEra objects
  events.json        // array of HistoricalEvent objects
```

These files are committed to the repo (or generated by a seed script). Next.js Server Components import them directly — zero network latency, zero infrastructure dependency, instant Vercel cold starts.

With 100–150 records the total payload for `shows.json` is under 200 KB before gzip. Client-side filtering (by genre, region, platform, accuracy score) runs in milliseconds in-memory.

**Text search:** Use `fuse.js` (fuzzy client-side search, ~24 KB gzip) rather than Algolia at this scale. It handles title + historical figures search with acceptable quality. Add Algolia later when the corpus exceeds ~500 entries or if editorial search quality becomes a priority.

**At the show detail page (SSG):** Each `/[locale]/show/[slug]` page calls `generateStaticParams` from the same JSON file. 150 shows × 2 locales = 300 pre-rendered pages at build time — well within Vercel's limits.

**Post-launch (user features):** Promote to Supabase PostgreSQL. The JSON schema maps 1:1 to the TypeScript interfaces in PRD section 7. Supabase can serve the full `shows` table via a single RPC at build time to replace the JSON import.

**Image storage:** Posters are served from their canonical source (TMDB, IMDb CDN) via `next/image` with `remotePatterns` configured. Add Cloudinary only if bespoke transforms (crop to 2:3, watermark) are needed; the default Next.js image optimizer covers WebP conversion and responsive sizes at no extra cost on Vercel.

## 3. Component Structure

### Layer Hierarchy

```
<TimelineRoot>                        // manages scroll container + yearToPixel mapping
  <TimelineScrollContainer>           // overflow:hidden, sticky inner, height:500vh
    <ParallaxLayer speed={0.4}>       // Layer 1 — era backgrounds
      <EraBackground era={} />        // one per era, absolutely positioned
    </ParallaxLayer>
    <ParallaxLayer speed={1.0}>       // Layer 2 — time axis
      <TimeAxis />                    // SVG or div ruler with year labels
      <EventMarkers events={} />      // dots/icons on the axis
    </ParallaxLayer>
    <ParallaxLayer speed={1.0}>       // Layer 3 — show cards
      <ShowCardTrack shows={filtered} pixelFn={yearToPixel} />
      // individual cards positioned absolutely by narrativeYearStart
    </ParallaxLayer>
  </TimelineScrollContainer>
</TimelineRoot>
```

### Server vs Client Component split

| Component | Boundary | Reason |
|-----------|----------|--------|
| `app/[locale]/page.tsx` | Server | Reads JSON, passes props down — zero JS bundle for data layer |
| `TimelineRoot` | Client | useScroll requires browser |
| `ParallaxLayer` | Client | useTransform requires browser |
| `ShowCard` | Server-compatible | Pure display, no interaction. Mark 'use client' only if you add hover animation |
| `FilterBar` | Client | User interaction, reads URL state |
| `ShowDetailPanel` | Client | Animation, portal |
| `app/[locale]/show/[slug]/page.tsx` | Server | generateStaticParams SSG, generateMetadata for SEO |

## 4. State Management

### What state lives where

| State | Owner | Why |
|-------|-------|-----|
| Active filters (genre, region, platform, score) | `nuqs` — URL search params | Shareable links, browser back/forward, teacher use-case (US-03) |
| Text search query | `nuqs` with debounce | Same — searchable URL |
| Selected show (detail panel open) | `nuqs` (`?show=slug`) | Deep-linkable show detail |
| Scroll position / progress | Framer Motion `scrollYProgress` motion value | Not React state — never triggers re-render |
| Filtered shows array | Derived — `useMemo` in `ShowCardTrack` | Computed from URL params + raw JSON |
| UI transient state (panel animation phase, tooltip hover) | Local `useState` | No persistence needed |

**No Zustand needed for v1.** Zustand adds value when you have cross-cutting client state that needs to be shared without prop drilling and cannot live in the URL. For this app all persistent state can be URL params; add Zustand only if user-account / watchlist state lands and needs a non-URL home.

**nuqs setup:**

```typescript
// app/[locale]/layout.tsx
import { NuqsAdapter } from 'nuqs/adapters/next/app';
export default function Layout({ children }) {
  return <NuqsAdapter>{children}</NuqsAdapter>;
}

// components/filters/FilterBar.tsx
import { useQueryStates, parseAsArrayOf, parseAsString } from 'nuqs';
const [filters, setFilters] = useQueryStates({
  genre:    parseAsArrayOf(parseAsString).withDefault([]),
  region:   parseAsArrayOf(parseAsString).withDefault([]),
  platform: parseAsArrayOf(parseAsString).withDefault([]),
  score:    parseAsString.withDefault(""),
  q:        parseAsString.withDefault(""),
  show:     parseAsString.withDefault(""),
});
```

## 5. Performance Architecture

### Image loading for 100+ posters

- Use `next/image` with `loading="lazy"` (default) — images outside viewport are not requested.
- Set `placeholder="blur"` with a pre-computed `blurDataURL` (10×15 px base64 JPEG, ~200 bytes each — store inline in `shows.json`). This eliminates layout shift on slow connections.
- Set explicit `width` and `height` on every `<Image>` to prevent CLS (Core Web Vitals).
- Mark the first 6–8 visible cards with `priority={true}` to preload above-the-fold posters.

### Virtualization — when to apply

With 100–150 cards positioned absolutely across a 20 000 px fresco, all cards are in the DOM simultaneously. Benchmarks suggest this is acceptable (150 divs with images is not a problem for modern browsers when images are lazy). However:

- **Do not use react-window** for the parallax card track. react-window virtualizes a linear scroll list; it cannot handle absolute positioning at arbitrary pixel offsets driven by a non-linear time scale.
- **Do apply IntersectionObserver** per card to trigger `will-change: transform` only when the card is within two viewport widths of the visible area. This avoids GPU memory waste from 150 simultaneously composited layers.
- If the corpus grows beyond 300–400 cards, implement manual DOM virtualization: compute the visible year range from scroll position, render only cards whose `narrativeYearStart` falls within `[visibleYearMin - buffer, visibleYearMax + buffer]`.

### Bundle size

| Library | Gzip size | When to include |
|---------|-----------|-----------------|
| Motion (Framer Motion) | ~32 KB | Always — core parallax |
| nuqs | ~6 KB | Always — filter state |
| fuse.js | ~24 KB | Always — search |
| react-window | ~8 KB | Post-launch only if >300 cards |
| Algolia InstantSearch | ~45 KB | Post-launch only if fuse.js quality insufficient |

Use dynamic `import()` for `ShowDetailPanel` — it is never needed until a card is clicked, so it loads lazily after the timeline is interactive.

### Timeline skeleton < 1 second

The page Server Component sends the era color gradients and time axis structure as HTML (zero JS). The `<SkeletonTimeline>` renders the era colour bands and blank card placeholders synchronously. Card images and poster data hydrate progressively.

## 6. SEO Architecture

### Page inventory and rendering strategy

| Route | Strategy | Reason |
|-------|----------|--------|
| `/[locale]` (timeline) | SSG + ISR (revalidate: 86400) | Main page must be indexable; data changes rarely |
| `/[locale]/show/[slug]` | SSG via `generateStaticParams` | Each show is a standalone SEO entity; full metadata |
| `/[locale]/era/[eraId]` | SSG | Shareable teacher links (US-03); era = historical keyword target |

**Show detail page metadata pattern:**

```typescript
// app/[locale]/show/[slug]/page.tsx
export async function generateStaticParams() {
  const shows = await getShows();
  const locales = ['en', 'fr'];
  return locales.flatMap(locale =>
    shows.map(show => ({ locale, slug: show.id }))
  );
}

export async function generateMetadata({ params }) {
  const show = getShowBySlug(params.slug);
  return {
    title: show.title[params.locale],
    description: show.historicalContext[params.locale].slice(0, 160),
    openGraph: {
      images: [{ url: show.posterUrl }],
    },
    alternates: {
      languages: { en: `/en/show/${show.id}`, fr: `/fr/show/${show.id}` },
    },
  };
}
```

**hreflang:** next-intl middleware automatically injects `Link: <url>; rel="alternate"; hreflang="fr"` response headers for every page, covering the bilingual SEO requirement without manual configuration.

## 7. i18n Architecture

### Recommended: next-intl with App Router, prefixed locale routes

**Folder layout:**

```
messages/
  en.json     // UI strings: nav labels, filter names, button text, ARIA labels
  fr.json     // Same keys in French
data/
  shows.json  // bilingual content: title.fr, title.en, historicalContext.fr, historicalContext.en
  eras.json   // name.fr, name.en, description.fr, description.en
```

**Key principle — split UI strings from content:**

UI strings (button labels, filter names, era legend) live in `messages/{locale}.json` and are accessed via `useTranslations()` or `getTranslations()`.

Show/era content (titles, synopses, historical context) is bilingual data embedded in the JSON data model (`title: { fr: string; en: string }`). These are NOT translation files — they are content fields. This distinction matters because:
- Show content is editorial, not translated programmatically
- Adding a new show does not require editing `messages/en.json`
- The CMS (post-launch) manages content fields, not i18n files

**Routing:** `/fr` and `/en` prefix routes, with `/` redirecting to `fr` by default (French-primary product). next-intl middleware handles the redirect and `Accept-Language` negotiation.

**Static rendering:** Use `setRequestLocale(locale)` in all layouts and page files to opt into static rendering (avoids the dynamic header read that forces SSR).

## Anti-Patterns to Avoid

### Anti-Pattern 1: Animating non-transform CSS properties on scroll

**What goes wrong:** Using `background-position`, `top`, `left`, or `margin` in scroll-linked animations triggers browser reflow/repaint on every scroll tick — guaranteed jank on mobile.

**Instead:** Animate only `transform: translateX()` (via `x` in Motion). Keep all parallax motion on GPU-composited properties.

### Anti-Pattern 2: React state for scroll position

**What goes wrong:** `useState` for scroll position causes the entire React tree to re-render on every scroll event (60+ times/second). Even with throttling, this will cause dropped frames.

**Instead:** Use Motion's `scrollYProgress` as a motion value. It never triggers React renders — it is a reactive value that drives CSS transforms directly.

### Anti-Pattern 3: `useEffect` + `addEventListener('scroll')` for parallax

**What goes wrong:** Scroll event listeners on the main thread compete with painting. Safari iOS throttles main-thread scroll handlers aggressively.

**Instead:** `useScroll` from Motion, which uses the native `ScrollTimeline` API where available and falls back to a passive RAF loop.

### Anti-Pattern 4: Separate message files per show

**What goes wrong:** Putting show titles and synopses in `messages/en.json` makes the file enormous, couples content changes to code deploys, and confuses translation tooling.

**Instead:** Bilingual fields inline in the data model (`title: { fr, en }`). The `messages/` files contain only UI chrome.

### Anti-Pattern 5: Opening the detail panel as a full page navigation

**What goes wrong:** Routing to `/show/[slug]` as a client navigation resets the timeline scroll position, breaking the immersive experience.

**Instead:** The detail panel is an overlay (drawer/modal) triggered by URL state (`?show=slug`) while the timeline page stays mounted. The static `/show/[slug]` route exists only for SEO and direct links — it renders the same content but in a standalone layout.

## Scalability Considerations

| Concern | v1 (100–150 shows) | v2 (500+ shows, user accounts) |
|---------|--------------------|-------------------------------|
| Data layer | JSON files | Supabase PostgreSQL + REST API |
| Search | fuse.js client-side | Algolia or Supabase FTS |
| Image CDN | next/image + source CDN | Cloudinary for transformation pipeline |
| Build time | < 2 min (300 SSG pages) | ISR to avoid rebuild per show addition |
| Scroll virtualization | All cards in DOM (150) | IntersectionObserver + manual DOM windowing |
| CMS | JSON in repo | Payload CMS or Directus with Supabase |
| State | nuqs | nuqs + Zustand (watchlist, auth) |
